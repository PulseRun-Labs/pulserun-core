# PulseRun Core — Soroban rebase

**Prepared 2026-11-22 · v0.3.0**

PulseRun Core was already a Rust and Soroban workspace when it was submitted: the escrow is a `#[contract]`, authorization uses `Address::require_auth`, time comes from the ledger, and settlement is denominated in SEP-41 tokens. The parts that were not fully Stellar-native were the scaffolding around it. Tests and the deploy script used a hand-written `MockToken` contract that lived in this repository, the wasm build relied on a `SOROBAN_SDK_BUILD_SYSTEM_SUPPORTS_SPEC_SHAKING_V2` workaround instead of the Stellar CLI, the workspace pinned `soroban-sdk 28.0.0`, and the testnet record still treated that toy token as the payment rail. This rebase removed those pieces so every path — tests, build, deploy, and documentation — runs on the canonical Stellar stack.

The central change is that settlement now runs on the Stellar Asset Contract. `contracts/mock_token` and its nine tests were deleted, leaving one contract in the workspace: `PulseEscrow`. The suite registers a real SAC with `Env::register_stellar_asset_contract_v2`, funds test accounts through `StellarAssetClient`, and asserts balances through `TokenClient`, so it exercises the same contract that moves XLM and issued assets on-chain rather than a lookalike. Because the SAC emits its own `transfer` events, event assertions were scoped to events published by the escrow, and two new escrow-level tests cover the real token boundary: a requester with no SAC balance cannot create a job, and a non-token `payment_token` address reverts the call. The suite is now 41 tests — the nine token-only tests left with the token, and two SAC-boundary tests were added. The SDK moved to `soroban-sdk 29.0.1` (protocol 29), the workspace version to `0.3.0`, and `Cargo.lock` was regenerated.

Around the contract change, the build and delivery path moved onto Stellar's own tooling. The documented and CI wasm build is now `stellar contract build`; the environment-variable workaround is gone, and CI installs `stellar/stellar-cli@v30.0.1` before building. `scripts/deploy-testnet.sh` no longer deploys a token: it resolves the SAC address for `PAYMENT_ASSET` (native XLM by default) with `stellar contract id asset`, deploys the escrow, calls `init`, and writes `PAYMENT_ASSET`, `PAYMENT_TOKEN_ID`, and `PULSEESCROW_ID` to `docs/deployments/testnet.env`. The README, architecture page, contract reference, developer and contributing guides, security scope, PR template, and deployment docs were all updated to describe the SAC-based design, and the v0.1.0 deployment is retained only as historical evidence. The only contract intended for deployment is `pulserun_escrow`; the SAC already exists on the network and is not something this project deploys.

Verification ran both locally and on-chain. Locally, `cargo fmt --all -- --check` and `cargo clippy --locked --all-targets -- -D warnings` are clean, `cargo test --all --locked` passes 41 tests, and `stellar contract build` produces a 20,637-byte wasm with hash `ac2afe1f…` and a 14-function ABI. On testnet, v0.3.0 is deployed at `CAPNQ4LWFOVVJG76UHGAOUT4RL4OH2LJKQOY36KYU5JQ7SEJ5F4DSI2D` with admin `GAFRQAM4VZDKUY5TL4PJFFLCAN5E7PPDXP3QCELHHMBP4QZZY54Q7IQP`, the native XLM SAC `CDLZFC3SYJYDZT7K67VZ75HPJVIEUVNIXF47ZG2FB2RMQQVU2HHGCYSC` as its payment rail, and a 60-second demo dispute window. A full job ran: 10,000,000 stroops were locked, a 20-second proof was submitted, an early claim was rejected with `DisputeWindowActive` (`Error #11`), and the post-window claim paid the runner 2,000,000 stroops, refunded the requester 8,000,000, and left the escrow at zero with the job `Settled`. The init, create, proof, and claim transactions, the wasm hash, and the deployment record are in the README and `docs/deployments/testnet.md`; CI and the docs deployment both passed. The admin on this testnet deployment is a throwaway key and should be replaced with a multisignature or governed account before any real-value use.
